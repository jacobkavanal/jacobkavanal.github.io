My Projects

Greening Earth ↗

GitHub

A 3D visualization showing one of our Earth’s more hopeful environmental trajectories.

Python · NumPy · rasterio · GeoJSON · Three.js

Details

Overview

Satellite rasters contain rich environmental information, but multi-gigabyte source files are not a useful starting point for someone exploring a map in a browser. This project connects the data-processing work to a visual question: how does vegetation differ across places and years?

My contribution

I built a Python pipeline using NumPy and rasterio to transform MODIS vegetation rasters into normalized cells. I also worked on the browser rendering and a custom binary grid format, so the visualization could use dense data without repeatedly transferring large GeoJSON objects.

Data format

GeoJSON is convenient for inspection and interchange, but repeating geometry and property names is expensive for a regular raster grid. A compact grid stores the spatial structure once and the values separately. The reader and writer share a format contract, trading general-purpose readability for smaller transfers and predictable decoding.

Evidence & results

The résumé records 592,800 cells per layer, a reduction from 349 MB of GeoJSON to an 8.2 MB binary representation, and a 1.2 MB initial load. It also records rendering more than 195,000 3D features in 12 ms. These are project benchmarks, not a guarantee for every device or network.

Interpretation

NDVI is a vegetation index, not a direct measurement of biodiversity or ecosystem health. A greener location is not automatically a healthier ecosystem. Comparing dates also requires attention to seasonality, missing data, and the source product. The map supports exploration; causal explanations require additional evidence.

What I would evaluate next

Benchmark the same regions and detail levels across devices, document the source product and observation windows directly in the interface, and test whether readers can distinguish vegetation intensity from change.

Mixify ↗

GitHub

A playlist-building app that helps Spotify users find tracks that mix well together based on BPM and musical key.

React · ReccoBeats API · Spotify Web API · Jest

Details

Overview

A song can fit someone’s taste and still be difficult to mix into a set. Mixify focuses on the transition between tracks: tempo, harmonic compatibility, and enough variety to keep the mix interesting.

My contribution

I built a React app for finding tracks, assembling a mix, and exporting it to a private Spotify playlist. ReccoBeats supplies audio features, while the Spotify Web API supports catalog and playlist workflows. The recommendation logic puts mixing constraints directly into the selection process.

Recommendation choices

The base tempo window is ±5 BPM. Half-time and double-time comparisons account for transitions that share a pulse at different apparent tempos. Camelot-wheel relationships provide a practical harmonic-compatibility rule. Filtering out the seed artist encourages variety rather than simply returning more of the same artist.

Recommendation approach

Tempo and key provide interpretable domain constraints and work without collecting a large listening-history dataset. A user can understand why a track was suggested. That makes the approach useful for a focused mixing tool, while leaving room for a later preference model.

Evidence & limits

The repository documents search, mix assembly, recommendations, and Spotify export. Tempo/key compatibility is a useful filter, not a guarantee of a good transition: phrasing, energy, arrangement, and the DJ’s intent still matter. API access and Spotify authorization are required for the original application; this case study does not depend on them.

What I would evaluate next

Ask DJs to compare the usefulness and diversity of suggestions, measure which recommendations they keep, and separate technical compatibility from subjective fit. Any ranking improvement should be tested against the simple, explainable baseline.

Liver risk stratification ↗

A machine learning project predicting liver-related health risks from patient histories, achieving a private-leaderboard C-index of 0.93473 and placing our team roughly in the top 5% of an international competition.

Python · NumPy · scikit-learn · Survival analysis

Details

Overview

Clinical follow-up is uneven. Patients have different numbers of visits, biomarkers are missing, and some patients leave observation before an outcome occurs. A useful model needs to account for trajectories and censoring rather than treating every row as a complete snapshot.

My contribution

For the challenge, I engineered patient-level trajectory features and worked with endpoint-specific survival models. The résumé reports 255 features for 1,676 patients with up to 22 visits, including FIB-4, APRI, biomarker trends, and missingness indicators.

Model choice

The submitted approach rank-blended Coxnet, Random Survival Forest, and XGBoost Cox predictions. These model families capture different relationships: regularized linear effects, nonlinear splits, and boosted risk functions. Rank blending combines relative ordering without assuming their raw prediction scales are comparable.

Validation

Project notes distinguish the official submission from a separate local model-family search. The best local cross-validation family was not the submitted ensemble. Sparse hepatic events made fold-level comparisons noisy, so local CV and private-leaderboard scores should not be presented as directly comparable estimates.

Evidence & results

¹ The résumé reports a private-leaderboard C-index of 0.93473 and 27th place in the official challenge. A C-index measures concordance in risk ordering; it is not classification accuracy or proof of calibrated individual risk. The exact score and placement are résumé-reported and have not been independently verified here against the leaderboard.

Limitations & next steps

This is a competition project, not a clinically validated decision system. Further work should examine target construction, missing-label handling, censoring assumptions, calibration, subgroup performance, and external validation. The repository notes include later target-correctness fixes, which must be kept separate from the scored submission.

Hospital data integration ↗

A research pipeline validating and joining CMS hospital quality, utilization, and financial data for analysis.

Python · REST APIs · SQL · SQLite

Details

Overview

Hospital datasets do not share the same grain or reporting period. Profiles describe hospitals, cost reports describe filings, and inpatient aggregates describe hospital–DRG combinations. A naïve join can multiply rows or attach an arbitrary financial report.

My contribution

As a research assistant at UC San Diego / Terizza AI, I worked on healthcare data integration. The local pipeline retrieves complete selected CMS releases, preserves original API responses, normalizes shared hospital identifiers, and validates records before publishing a SQLite snapshot.

Design decisions

The pipeline keeps the sources in separate tables and joins them at query time. Identifiers remain text to preserve leading zeros and legitimate alphanumeric values. Missing markers become SQL NULL while their original representation is retained. A staged refresh protects the last published database if validation fails.

Join rules

When multiple cost reports could match a hospital, the result is marked ambiguous and financial values are withheld. A report must overlap the inpatient year, but overlap alone does not imply calendar-year comparability. Current ratings also should not be interpreted as historical ratings.

Evidence & validation

The October 22, 2026 verification recorded 5,419 hospital profiles, 6,109 cost reports, and 145,879 inpatient aggregate rows. The joined view preserved 145,879 rows. Repeat ingestion detected no record changes. Tests cover pagination, duplicate keys, missing values, ambiguous joins, and preservation of the previous database after failure.

Limits & next steps

This local research pipeline does not establish production scalability or a transactionally consistent snapshot across CMS APIs. Hospital-wide financial values repeat across DRGs and must not be summed across the join. Company ownership mapping needs a separate, dated crosswalk. A natural next step is making these quality flags easier to inspect.

Semantic extraction agent ↗

An LLM-assisted agent that interprets unfamiliar dataset columns from metadata, checks column coverage, and saves versioned JSON results for review.

Python · LLM APIs · JSON

Details

Overview

A data lake can contain technically valid datasets that are still difficult to use. Column names, types, and summary statistics do not always explain units, encoded categories, or the intended meaning of a field. Semantic interpretation helps bridge that gap, but introduces the risk of confident unsupported claims.

My contribution

In our D37 capstone team, I built the LLM-assisted semantic extraction agent. It consumes metadata profiles, batches one request per dataset, validates that the returned interpretations cover the requested columns, and saves versioned JSON outputs. Teammates own the metadata and downstream integration/evaluation components.

Batching

Dataset-level context lets the model interpret related columns together. It also avoids a separate request for every field. Coverage validation checks structural completeness, while numbered output files preserve previous runs for comparison instead of silently overwriting them.

Evidence & results

The initial saved outputs cover 15 cardio columns and 16 heart columns. The repository documents standalone execution and an offline integration path that reuses saved interpretations. These artifacts demonstrate the workflow; column coverage is not a measure of semantic accuracy.

Uncertainty

Interpretations based on names and statistical profiles can be ambiguous. Unsupported units or category mappings need verification against authoritative dictionaries. The project uses AI-assisted development, with team members responsible for architecture, reviewing outputs, and interpreting results.

Limits & next steps

Reliable evaluation needs each set of human judgments matched to the exact semantic run under review. Extending the agent to imaging metadata also requires a different structure from CSV columns. Both are reasons to preserve evidence and schema-specific limitations rather than treating all metadata as interchangeable.
